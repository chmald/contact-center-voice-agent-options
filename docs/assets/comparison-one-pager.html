Azure AI Voice Live API vs Azure OpenAI GPT Realtime API (GA deep dive)

Bottom line: two-GA-API deep dive. The repo also includes a Foundry voice agent public preview; see the root README for the full three-way table. Same model family, same browser app, same Python bridge pattern; the difference is who manages deployment, capacity/quota, voice/audio processing, and lifecycle risk.

Use Voice Live when...

  • You want managed models and no model deployment.
  • You prefer per-resource Voice Live limits over per-model deployment quota.
  • You need Azure neural/HD/custom voices, built-in transcription, semantic VAD, noise suppression, echo cancellation, Avatar, BYOM, or agent mode.
  • You can request new-connections/min increases when concurrency requires it.

Use Realtime when...

  • You need model version, deployment name, capacity, and upgrade control.
  • You already have realtime quota and regional capacity.
  • You need the GA nested schema, WebRTC ephemeral tokens, or direct SIP on the realtime surface.
  • You accept no PTU, constrained regions, quota forms, and lifecycle-date management.
Third option: Foundry voice agent is public preview. It stores instructions, tool declarations, voice, greeting, audio settings, versions, traces, and transcripts in a Foundry project; the bridge sends no session config and executes the tools (shared RAG). Its default is the project route /api/projects/<p>/agents/<a>/endpoint/protocols/voice, with managed models and no deployment. It shares Voice Live limits with the Voice Live app in shared-platform mode. Do not treat it as production-ready.

Capacity implication

Formula: p90 TPM/call x concurrent calls. Example: ~80K TPM/call x 20 calls ~= 1.6M TPM. Both APIs need sizing; Voice Live and the voice agent shift from deployment quota to per-resource connection/TPM limits; in shared mode they share the same limit.

Reduce tokens: shorter instructions/tools, concise answers, history cap/delete, realistic load tests. Unheard-audio conversation.item.truncate remains future hardening, not implemented.

Confirm before cutover: approved quota/limit increase, validated region capacity, p90 TTFA, busy count, and rollback path.

Migration path and reproduction

  1. Change endpoint, auth scope if needed, and RBAC.
  2. Remove or add model deployment depending on direction.
  3. Reshape session.update flat ↔ nested.
  4. Map events; shared bridge already accepts both.
  5. Pick voice/VAD/noise/transcription options.
  6. Load test; request Voice Live connection increase or Realtime quota before cutover.

First pin the tenant: az login --tenant <TENANT_ID>, azd auth login --tenant-id <TENANT_ID>, then per example azd env set AZURE_TENANT_ID / AZURE_SUBSCRIPTION_ID / AZURE_LOCATION. Never a bare azd up.

Deploy: cd examples\voice-live-api, cd examples\realtime-api, or cd examples\foundry-voice-agent, then azd up. For the voice agent, profile edits require azd hooks run postprovision.

See deployment, testing, and architecture. Keep both behind the same bridge interface until cost, quality, and capacity pass.
